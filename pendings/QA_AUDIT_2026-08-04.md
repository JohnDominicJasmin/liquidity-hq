## 1. 🔴 Highest severity

### 1.1 The browser makes ~450 direct calls to Binance per page load, on every route

**This is the finding to action first.** It is an architecture issue, not a bug
in one file.

Measured on `/refund` — a *static legal page* with no market content:

| Metric | Value |
|---|---|
| Third-party requests in first second | **575** |
| Total over 12s | **618** |
| → `api.binance.com` | 319 |
| → `fapi.binance.com` | 127 |
| → `api.bybit.com` | 165 |
| Steady-state after mount | ~3 req/s, indefinitely |

Not a retry loop — it is a **one-shot fan-out on mount** (coins × timeframes)
plus a persistent poll. `MarketProvider` is mounted app-wide, so *every* route
pays this, including `/privacy`, `/terms`, `/refund`, `/disclaimer`.

**Why it matters — the calls come from the user's browser, so it is the user's
own IP that Binance rate-limits, not the server's.**

Corroborating evidence, measured on this dev machine:

```
$ curl -s -o /dev/null -w "%{http_code}" "https://api.binance.com/api/v3/ticker/24hr?symbol=BTCUSDT"
418
```

`418 I'm a teapot` is Binance's documented **IP-ban** response, returned after
repeated rate-limit violations. This machine is currently banned. The most
likely cause is this app, during development. In the browser the ban surfaces
as a CORS error (the 418 carries no `Access-Control-Allow-Origin`), which is
why the sweep logged **15,233 failed Binance requests across 64 page-loads**.

A normal user browsing 3–4 pages in a minute issues well over a thousand
Binance requests. That is ban territory. Once banned, market data silently
stops working *for that user*, on *every* device behind that IP, and the app
shows no explanation.

| | |
|---|---|
| **Files** | `components/MarketProvider.tsx` (1461 LOC, ~30 fetch sites), `lib/sparklineData.ts`, `lib/ribbonCandles.ts`, `app/arena/page.tsx`, `app/correlation/page.tsx`, `app/funding/page.tsx`, `app/liq/page.tsx`, `components/KLineProChart.tsx` + 5 more |
| **Repro** | `npm start`, open `/refund`, DevTools → Network, filter `binance`. Count. |
| **Expected** | A static legal page issues zero market-data requests |
| **Actual** | 446 Binance + 165 Bybit |

**Fix direction** (dev session's call, but the shape is fairly forced):

1. **Don't mount `MarketProvider` on routes that don't render market data.** Cheapest win, no new infrastructure. Kills the cost on ~8 static/legal/auth routes outright.
2. **Proxy Binance through the app's own API routes** and wrap in `cached()` per `AGENTS.md` convention. Moves rate-limit exposure to one server IP that you control and can cache — instead of every user's IP. This is the real fix.
3. **Collapse the fan-out.** 385 distinct URLs per load is a lot of round-trips regardless of who makes them; batch endpoints exist for tickers.
4. **Surface the failure.** `lib/sparklineData.ts:34` swallows the error (`catch { /* network hiccup */ }`). Per `HANDOVER.md` §14 — *"a broken button just looks like a failed check"* — a total market-data blackout currently renders as "no data" with no explanation.

⚠️ Item 2 has a cost implication (server egress) and changes the `cached()`
story — worth an explicit owner decision before building.

### 2.3 🔵 `cronAuth` accepts the secret in the query string

`lib/cronAuth.ts:24`

```ts
const provided = req.headers.get('x-cron-secret') ?? new URL(req.url).searchParams.get('secret') ?? '';
```

A secret in a query string is written to Cloudflare and Render access logs in
plaintext, and leaks via `Referer` on any outbound navigation. The header path
is already the one all live cron-job.org jobs use (`HANDOVER.md` / `INFRASTRUCTURE.md` §2).

**Fix:** drop the `searchParams` fallback — header only. ⚠️ Confirm no n8n
workflow relies on the query form first; per `CLAUDE.md`, those schedulers live
outside this repo and are invisible to code search.

### 2.4 ⚪ `rateLimit` is per-process, correct only while Render runs one instance

`lib/rateLimit.ts:6` — an in-memory `Map`. The file comment states the
assumption explicitly and it is true today. Recording it because the failure is
silent: scale to 2+ instances and every limit multiplies by the instance count
with nothing in the logs to say so. `getClientIp()` correctly prefers
`cf-connecting-ip`. No change needed now; revisit at the same time as any
scaling change.

### 2.5 ⚪ CSP still allows Google Fonts after fonts were self-hosted

`next.config.ts:31,33` allow `fonts.googleapis.com` / `fonts.gstatic.com`,
though commit `ad61e05` self-hosted Figtree and IBM Plex Mono. Line 24 documents
this as a deliberate defensive fallback — so it is **intentional**, not drift.
Noted only so a future reader doesn't re-derive it. Removing them would tighten
CSP slightly.

| Route | Element | Placeholder |

### 4.3 🟡 Colour contrast — 32 confirmed AA failures

> **This section was rewritten after the first pass was found to be wrong.**
> The original table listed 12 pairs computed *without* compositing `rgba()`
> backgrounds or ancestor `opacity`. This codebase uses both heavily
> (`withAlpha(color,'14')` is a documented convention), so those numbers were
> materially wrong in both directions. Three of the four `/hours` entries were
> **false positives** — recomputed with alpha + opacity they are ASIA **4.88**,
> LONDON **5.63**, NY **6.35**, all of which *pass*. Every number below is from
> the corrected checker, restricted to fully-opaque text (effective opacity
> ≥0.95) so nothing faded or collapsed is counted.

WCAG 1.4.3 AA needs 4.5:1 for normal text, 3:1 for large text (≥24px, or ≥18.7px bold).

**Cluster 1 — `/scanner` table headers are effectively invisible. Worst finding.**

| Ratio | Text | Colours |
|---|---|---|
| **1.55** | "Coin", "15 Min", "1 Hour", "4 Hour", "1 Day", "Squeeze" (6 column headers) | `rgb(51,51,51)` on `rgb(11,12,15)` |
| **1.59** | "Scale:", "via CoinGecko" | `rgb(51,51,51)` on `rgb(6,7,10)` |

`#333` on `#0B0C0F` is near-black on near-black. These are the column headers of
a core feature — hard to read on a good monitor, unreadable on a phone in daylight.

**Cluster 2 — grey secondary text on near-black**

| Ratio | Where | Text | Colours |
|---|---|---|---|
| **2.07** | `/research` | "Y axis: price multiple from halving date", "2024 via Bybit" | `rgb(68,68,68)` on `rgb(6,7,10)` |
| **3.20** | `/dashboard` | "No data", "Balanced positioning" | `rgb(96,96,96)` on `rgb(6,7,10)` |

**Cluster 3 — 🔴 the brand blue fails with white text, app-wide (systemic)**

| Ratio | Colours | Affects |
|---|---|---|
| **3.98** | `rgb(255,255,255)` on `rgb(26,122,255)` | Every active nav pill (`Scanners ▾`, `Tools ▾`, `Arena`, `Dashboard`, `News`) **and the primary CTA** — "Get Started", "Get Started Free" |

This is one design token, not a page bug — **`#1A7AFF` with white text is 3.98:1
and needs 4.5:1.** It is on the main conversion button, so it is both the
highest-traffic and highest-value instance. Darkening the blue to roughly
`#0F6BEF` clears AA while staying on-brand; alternatively increase the CTA font
to ≥18.66px bold, which drops the requirement to 3:1. **Fix the token, not the
32 call sites.**

⚠️ **Confidence note.** I rebuilt this checker three times and it was wrong each
of the first two times (`color(srgb …)` parsing, then un-composited alpha, then
counting `opacity:0` collapsed menus). The numbers above are the ones that
survived, but automated contrast checking is clearly fragile against this
codebase's token system. **Before acting on this section, run a real tool**
(axe-core, Lighthouse, or Chrome DevTools' own contrast picker) to confirm.
Treat this as "here is where to look", not as a final measurement. Elements
below 0.95 effective opacity were excluded entirely and are **unmeasured**, not
proven-good.

## 5. Correctness bugs

### 5.1 🟡 React hydration mismatch on `/briefing` (error #418)

Observed as an uncaught page error on **both** desktop and mobile runs:

```
Minified React error #418  (args: "text")
```

`#418` = *text content does not match server-rendered HTML*.

**Root cause** — `app/briefing/page.tsx`:

```
194:  const [now, setNow] = useState<Date>(localNow);   // clock read at first render
...
257:  const h = now.getHours(), m = now.getMinutes();
258:  const timeStr = `${pad2(h % 12 || 12)}:${pad2(m)} ${h >= 12 ? 'PM' : 'AM'} ${localZoneAbbr()}`;
259:  const dateStr = `${days[now.getDay()]}, ${months[now.getMonth()]} ${now.getDate()}`;
```

The page is `'use client'`, but Next still server-renders it on first load.
`localNow` runs once on the server and again on the client. `timeStr` embeds
**minutes and `localZoneAbbr()`** — the server is UTC on Render, the client is
the viewer's zone — so the two renders essentially always disagree.

**Repro:** load `/briefing`, watch the console. Intermittent in practice
(React silently recovers from some text mismatches), reproduced 2 of 3 attempts.

**Fix direction:** render a stable placeholder on the server and set the real
clock in a `useEffect`, or mark just that text node
`suppressHydrationWarning`. Do **not** just silence it globally — the same
pattern may exist elsewhere.

**Correction to an earlier hypothesis:** `app/briefing/page.tsx:136`
(`nowUtc` via `toLocaleString`) is **not** the cause — that string is built for
the Grok prompt and never rendered to the DOM. Ignore it.

### 5.2 ⚪ `/api/labels` fetch aborts on unmount

component unmounts mid-flight. Harmless — the request is genuinely no longer
needed — but it is console noise that makes real network failures harder to

`/` is titled just **"LiquidityHQ"**. Same for `/login`, `/forgot-password`,
`/offline`, `/ops/login`. The homepage title is the single highest-leverage SEO
field and currently carries no keyword. Something like
*"LiquidityHQ — Crypto Trading Intelligence & Signal Analytics"* (~60 chars)
would fit the SERP limit.

`/ops/login` should additionally carry `noindex` — it is an internal admin
surface. `robots.txt` does not currently disallow `/ops`.

### 6.6 🔵 No structured data anywhere

**0 JSON-LD blocks** across all 32 pages. Highest-value additions, in order:
`Organization` + `WebSite` on `/`, `FAQPage` on `/faq` (eligible for rich
results), `Product`/`Offer` on `/upgrade`, `BreadcrumbList` sitewide.

### 9.2 Two false alarms, recorded so nobody re-chases them

**`/login` "stuck on Loading… forever" — NOT a bug.** Mid-audit, `/login` sat on
the `app/loading.tsx` Suspense fallback indefinitely (0 inputs at t+25s) with:

Refused to execute script from '.../_next/static/chunks/turbopack-0neq9yelvz_w8.js'
because its MIME type ('text/plain') is not executable

Cause was **stale `.next` artifacts** — exactly the trap `HANDOVER.md` §8

before investigating anything else.

**A whole audit run rendered unstyled.** One intermediate sweep reported 3,315
sub-24px tap targets (vs the true 159) and a phantom `/correlation` overflow.

type…` — the CSS 404'd, so pages rendered with no stylesheet, the *desktop* nav
was visible at 375px, and every element collapsed to inline size. Four routes
also returned 500. **The harness now asserts `document.styleSheets.length > 0`
and a themed `body` background before it will report numbers from a page.**
Any responsive audit of this app without that guard is untrustworthy.

**Known-flaky things this run confirmed** (add to `HANDOVER.md` §8's list):

- `Get-Content -Raw` fails in this PowerShell on paths containing `[` `]`
  (Next.js dynamic-segment directories) — use `bash`/`Grep` for those.
- `fetch()` normalises `..` in URLs *before* sending, so `/api/admin/../ops/users`
  never tests path traversal. Use percent-encoded `%2e%2e` for a real test.
- A CSS contrast checker must handle `color(srgb …)`, not just `rgb()`/`rgba()`
  — mine didn't, and produced two confident false positives (see §4.3).
